How the earlier "41 fps" and "46 fps" readings came about, for the record:
- First run after the pass, on mains: home 41 fps, project 48-52, others 55-60. The desktop app's own preview
  pane was rendering the site and using about half the GPU.
- Runs on battery: every view 45-47 fps with the same 23-24 ms cadence whatever is drawn (battery pacing).
- Two real faults were found while chasing this and are fixed: (1) my first change to the resolution scaler
  ("fall back to the lowest size when it keeps flipping") was triggered on fast machines too, because the
  library counts every upward step as a flip, so cheap views were being drawn at 1344x756 for nothing; (2) a
  first rewrite mistook a view locked at half the refresh rate (even 33 ms frames) for a battery-paced browser
  and left home at 39 fps. The scaler is now a small deterministic one: start sharp, step down only on missed
  refreshes measured against the fastest interval the device has shown, never retry a size that failed.
- Cost reductions made along the way and kept: MSAA capped at 2x (was 4x at 1x pixel density), bloom at half
  resolution, three noise lookups removed from the star and corona and five from the gas giant, the dust disc
  not drawn from the surface.

Re-run on the final code after the scaler change: type-check clean, build OK (7.0 MB), 37 captures with 0
console errors, journeys 20/20 on laptop, phone and reduced motion, hidden extras 17/17, studio 15/15, and
`shader-links.mjs --desktop` shows no slow link after the loader lifts (during loading: 0.5-2.1 s each for the

## Owner feedback round (2026-11-25, captures `c1`, `c2`, `s4`, `read1`, `strips`, `ret`)

The owner reported: the sun looks bad; visuals glitch in Firefox; the screens are too small and scrolling
should zoom; the return to the home planet puts the camera under the planet.

How each was reproduced:
- **Return path.** `tools/qa/return-trace.mjs` (new) drags the system view with real mouse input, calls the
  return and logs the camera every frame. From the default view the path was clean. From turned views the
  camera started up to 7.5 km below the home planet's horizon (az -90, tilt -16) and, at az 180, passed 1.2 km
  from the enlarged globe before whipping round. Frame sheets: `tasks/captures/ret/`.
- **Firefox.** playwright-core drives the installed Firefox 160/161 (`channel: 'moz-firefox'`). Still frames
  matched Chrome. `tools/qa/pace.mjs` (new) showed the problem in motion: the launch at 13-15 frames per half
  second with freezes of 1.6 s, 1.0 s and 0.7 s; a 0.94 s freeze in the middle of the return. Chrome had the
  same faults at smaller size (launch 16-18 frames per half second, one 0.62 s freeze).
- **Cause of the freezes** (found by diffing the source of shader programs linked mid-transition): the number
  of point lights changed from 2 to 1 whenever the lander was hidden, which makes three.js recompile every
  material. Plus: the 4096 x 4096 soft shadow map was re-rendered every frame of the lift-off.
